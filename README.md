# terraform-elasticstack-workspace

An OpenTofu module that turns one **workspace** id into a ready-to-use
place in the homelab's Elastic Stack: a Kibana space, data views for the
workspace's data, viewer and editor roles bound to groups, and baseline
dashboards and alerts. A workspace then adds its own dashboards and rules
without touching anyone else's.

It's used by
[`homelab-proxmox-platform`](https://github.com/BCochofelHomelab/homelab-proxmox-platform),
one stack per workspace, and takes its conventions and guardrails from
[`homelab-proxmox-core`](https://github.com/BCochofelHomelab/homelab-proxmox-core).

## Vocabulary

| Term | Meaning |
| --- | --- |
| **Workspace** | Observability data and resources with **one owner and one audience**: the unit of access, alert ownership and automation. Its id is permanent; its display name can change. |
| **Namespace** | The last part of a data stream's name, `<type>-<dataset>-<namespace>`. The namespace **is** the workspace id. |
| **Data view** | A Kibana object that selects data streams by pattern (`logs-*-<id>`). It selects data; it never grants access. |

Workspace ids allow only `a-z`, `0-9` and `_` (a namespace can't contain
`-`), and never `default`.

## What a workspace gets

| Capability | Resources |
| --- | --- |
| A Kibana space: display name, description, colour, solution view | `elasticstack_kibana_space` |
| One data view per data type, `<type>-*-<id>`, with deterministic ids (`<id>-<type>`), and the default one | `elasticstack_kibana_data_view`, `elasticstack_kibana_default_data_view` |
| `read_from`: another workspace's data, approved by its owner: a data view and read privileges per type | the same, plus the roles below |
| Roles `workspace-<id>-viewer` (reads the space) and `workspace-<id>-editor` (all of the space), both read-only on the data | `elasticstack_kibana_security_role` |
| Role mappings from groups (optionally one realm) to those roles; no groups, no access | `elasticstack_elasticsearch_security_role_mapping` |

Baseline dashboards, alerting rules and a workspace's own content come
next. What the module deliberately leaves out (Fleet, integration
packages, ILM, templates, pipelines) and why:
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Usage

Pin a release by its exact tag (no `v`):

```hcl
module "workspace" {
  source = "git::https://github.com/BCochofelHomelab/terraform-elasticstack-workspace.git?ref=1.0.0"

  workspace_id = "otel_demo"
  display_name = "OpenTelemetry demo"
  read_from    = ["platform"]

  access = {
    realm         = "oidc1"
    viewer_groups = ["otel-demo-viewers"]
    editor_groups = ["otel-demo-editors"]
  }
}
```

The caller configures the `elastic/elasticstack` provider, with both an
`elasticsearch {}` and a `kibana {}` block (the provider reads
`ELASTICSEARCH_*` and `KIBANA_*` from the environment only when the block
exists). A full example: [`examples/self-managed`](examples/self-managed).
Releases and versioning: [`docs/RELEASING.md`](docs/RELEASING.md).

## Getting started

Everything a contributor needs, from a clone, on Linux (Ubuntu or WSL2):

```bash
mise trust && mise install   # the pinned toolchain, git hooks, TFLint plugins
mise run check               # what CI runs
mise run test                # unit tests (mocked provider)
mise run test:integration    # a throwaway Elasticsearch + Kibana in Docker
```

How a change flows, and the rules it follows:
[`CONTRIBUTING.md`](CONTRIBUTING.md).
